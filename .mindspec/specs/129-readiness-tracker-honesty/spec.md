# Spec 129-readiness-tracker-honesty: Readiness and tracker honesty — spec-scoped selection, bd row caps, MF-2/MF-3 truth, scoped overrides (spec-128 follow-on, part 1 of 2)

*Citation scope: every code citation in this document names a function, symbol, file, or template — never a line number — and was verified against `main` at `e2325e36` (v0.15.0) on 2026-10-18 in the spec-129 worktree. Where the consolidated diagnosis this spec was drafted from turned out to be imprecise, the correction is recorded in § Background under "Corrections to the diagnosis".*

## Goal

After this spec, the verbs that decide *what work is ready* tell the truth about the tracker and about git:

- (a) `mindspec next --spec <id>` never reports an empty ready set in a way that is indistinguishable from "this spec has no work left": a bd-ready bead the binary can resolve by ID is either selectable or named with the exact reason it is not, a supplied selector (positional ID or `--pick`) on an empty set is refused rather than ignored, and the empty-set result carries the spec's derived lifecycle state so no caller can mistake "nothing ready" for "done" (GH #255; the readiness-truth face spec 128 deferred here by name);
- (b) no bd `ready`/`list` query the binary makes a decision on is silently truncated by bd's default row caps (100 for `ready`, 50 for `list`) — this repository has 106 ready beads today, so unscoped `mindspec next` is truncated *now*;
- (c) every bead and epic the binary creates for a spec carries one queryable spec-linkage datum, and spec-scoped selection reads it, so membership is a tracker fact and not a title-substring guess;
- (d) the MF-3 readiness signal never fails with "no landed merge into `<spec-branch>` names `bead/<id>`" when a correctly named merge of that bead IS an ancestor of the spec branch tip (GH #239), never holds a non-spec dependency to the landed-merge test, never lets a stale earlier-round panel registration pre-empt a correct corroboration, and prints what is actually true for a contradiction or a revert; GH #232 is dispositioned on evidence (no remote ref is read anywhere on this path) rather than by building a remote-aware feature;
- (e) the MF-2 token resolver recognises the same claim forms on both sides — bead text and spec text — so `R9(a)` against a spec that writes `R9(a)` resolves, and `AC9` is not silently skipped;
- (f) `--allow-not-ready` is scoped to the named failing signal(s), refuses when any *other* signal fails, records an evidence file in the durable override marker, and `mindspec bead ready-check` reads that marker back so the override log can be audited against the currently failing set (the "override log becomes misleading" cost GH #239 names);
- (g) ADR-0045 ("The binary owns sequence and rules; skills are harness adapters") lands as Accepted, so later specs (130–133) can cite it.

### Settled facts inherited from spec 128 (binding — not relitigated)

1. **The ready set is ONE construction on both paths.** `next.BuildReadySet` (`internal/next/beads.go`) is the shared bd-ready query + spec-title filter consumed identically by the claim path (`cmd/mindspec/next.go`'s `RunE`) and `runEmitOnly`; `--pick N` names the same bead on both; an explicit `--spec` whose epic cannot be resolved REFUSES via `scopeResolutionRefusal` and never widens to global `bd ready` (128 R6.7/AC-15). A non-empty raw set that the title filter reduces to empty is a loud error (`emptyAfterFilterError`, 128 R6.3(c)/AC-10b). The old "global-fallback/cap" explanation of #255 is therefore gone; what remains is the membership and emptiness honesty face this spec owns.
2. **`mindspec next` adopts ADR-0041's preflight leg for readiness** (the "fourth-verb clause"): `next.GateReadiness` runs after selection and before any mutation; `--allow-not-ready` records a durable marker via `next.RecordReadinessOverride` BEFORE `ClaimBead`, fail-closed; `next.RollbackReadinessOverride` deletes it on claim failure.
3. **`internal/validate` is an ADR-0030 enforcement package** (`internal/lint/boundary_test.go`'s `enforcementPkgs`): `internal/validate/readiness` may not import `os/exec` or `internal/gitutil`; its git read (MF-3) reaches git through `internal/lifecycle.FindLandedMerge`, which is NOT an enforcement package and may call `internal/gitutil`. New git primitives this spec needs live in `internal/gitutil`; new predicate logic lives in `internal/lifecycle`.
4. **Spec 125's exact-equality corroboration rule** (`ADR-0041` § Amendment (Spec 125)): a landed merge is identified only by a subject-scan candidate whose second parent is corroborated exactly by one of (b) a surviving bead-branch tip, (c) a registered panel's `reviewed_head_sha`, (d) an existing landed binding. Ancestor-tolerant confirmation is the removed misattribution vector and is not reintroduced here.

### The live evidence, verified 2026-10-18

**A. Spec-scoped `next` drops a ready bead (#255).** `BuildReadySet` with a spec flag runs `QueryReadyForEpic` → `bd ready --parent <epic> --json`. bd documents `--parent` as "Filter to descendants of this bead/epic". A bead that belongs to the spec by title but is not a descendant of the epic is therefore absent from `ReadySet.Raw` and never counted by `ExclusionNotice` (which counts only *title-filter* drops of items that WERE returned). On the claim path, the `len(items) == 0` branch in `RunE` runs BEFORE the positional/`--pick` selector is consulted: `mindspec next <bead-id> --spec X` on an empty scoped set prints "No ready work found." and exits 0 with the positional silently ignored; `--pick 3` on the same set is equally ignored. On `--emit-only` the same emptiness exits 1 ("no ready work found for --emit-only"), and a positional there goes to `next.FetchBeadByID` (readiness and membership never checked, by 128 R6.1's pinned preview semantics) — which is exactly why the issue's bead "resolves by ID" while the scoped query drops it. Two related defects: `ReadySet.ExclusionNotice` renders a count without bead IDs (`emptyAfterFilterError` does render IDs); and the empty-set text is the same sentence whether the spec is in `review` with everything closed or in `implement` with every open bead blocked.

**B. bd row caps.** Live: `bd ready --json` returns 100 rows and prints on **stderr** "Showing 100 of 106 ready issues. Use --limit 0 for all, or --limit N to raise the cap." (bd 1.1.0; `-n, --limit int … use 0 for unlimited (default 100)`; `bd list` defaults to 50). `bead.tracedOutput` (`internal/bead/bdcli.go`) runs `cmd.Output()`, so stderr is retained only inside `exec.ExitError` on *failure* — a successful truncated call discards the notice. Uncapped call sites today, re-derived by grep of every `"ready"`/`"list"` bd argv: `next.QueryReady`, `next.QueryReadyForEpic`, `next.ResolveActiveBead` (`bd list --parent … --status=in_progress`), `lifecycle`'s `listClosedBeadsFn` (`orphans.go` — an epic with more than 50 closed children can miss orphans) and `listOpenBeadsFn` (`stale_open.go`), `bead/hygiene.go`'s two `ListJSON("--status=open")` calls, and `complete`'s `runBDFn("ready", "--parent", …)` in the post-close next-bead lookup (reads `ready[0]` only — the cap cannot change element 0, so harmless, but it is still a cap site). Already passing `-n 0`: `phase.Cache`'s three `listJSONFn` calls, `approve/adopt_lattice.go`'s `adoptListBDFn`, and `approve/plan.go`'s `queryExistingChildren`. Deliberately NOT a cap defect: `internal/doctor/beads.go`'s `bd list --json` schema-drift probe reads no rows, only the error signature.

**C. No queryable spec linkage at creation.** `approve/plan.go`'s bead `bd create` passes `--parent <epic>` and `--metadata {"spec_id":…,"file_paths":…}` only; `approve/spec.go`'s epic `bd create` passes `--metadata {"spec_num","spec_title","mindspec_phase"}` — no `spec_id`. Nothing in selection reads `metadata.spec_id` (`next/mode.go`'s `parseSpecID` reverse-derives it from the TITLE). bd 1.1.0 offers `bd create --spec-id` (a link field with no `ready`/`list` filter — `bd show --json` does not even expose it), `--labels` (filterable), and `bd ready/list --metadata-field key=value` (filterable, repeatable). So the one datum plan approve already writes — `metadata.spec_id` — IS queryable today; it is simply not written on the epic and not read anywhere.

**D. MF-3 false negatives (#239; #232 shares the causes).**
1. *Over-broad dependency set.* `readiness.fetchBeadRecordReal` collects every `blocks` edge on the bead; `evaluateMF3` holds EVERY closed one to `findLandedMergeFn(root, specBranch, dep.ID)` with no spec-membership check. A closed plain task or a bead of another spec can never have a `bead/<id>` merge into THIS spec branch, so it fails MF-3 by construction. REPRODUCED.
2. *First-parent-only candidate scan.* `lifecycle.FindLandedMerge` generates candidates from `firstParentMergesFn` = `gitutil.FirstParentMerges` = `git log --first-parent --merges <ref>`. A correctly named two-parent merge that is an ancestor of the tip but off the first-parent chain (the issue's shape: later `main`-side merges and a sibling-branch merge above it; or a PR merge followed by a fast-forward) is never a candidate, so the result is `ErrLandedMergeNoCandidate`. REPRODUCED.
3. *Stale panel corroboration.* `lifecycle.reviewedHeadSHAForBead` returns the FIRST registration with a non-empty `reviewed_head_sha` in `panel.ForBead(panel.Scan(roots…))` order; `panel.Scan` sorts registrations by directory path. Per-round slugs such as `<bead>` and `<bead>-r2` sort the stale round first, and `FindLandedMerge` returns the exact-equality *contradiction* for that SHA BEFORE the surviving-tip and landed-binding legs are consulted. REPRODUCED; the likeliest real-world cause.
4. *Misleading message.* `ErrLandedMergeNoCandidate` wraps `ErrLandedMergeNotFound`, and so do the contradiction and revert returns; `evaluateMF3` discriminates only `*LandedMergeNoEvidence` and `errors.Is(err, ErrLandedMergeNotFound)`, so a contradiction or a revert prints the zero-candidate sentence "no landed merge into … names bead/X", which is false when a correctly named merge exists. The lifecycle layer already distinguishes the cases; the readiness arm collapses them.
- *#232 ("validates against origin/<spec-branch>").* There is NO `origin/` or remote-tracking read anywhere on this path: not in `internal/validate/readiness`, not in `lifecycle.FindLandedMerge`/`reviewedHeadSHAForBead`, not in `gitutil.FirstParentMerges`, not in `panel.Scan`. A local spec branch ahead of its remote PASSES today. #232's reproduction (local-only merge, first dependency edge, immediate MF-3 FAIL with the zero-candidate sentence) fits cause 1 (the dependency edge's target) or cause 3 (a stale panel registration). It is closed by this spec's fixes with that evidence (R4.5, AC-11); no remote feature is built.

**E. MF-2 token parser.** `readiness.claimTokenRe` is `\b(R|AC-)([0-9]+)([a-z])?\b`. `extractLineClaims` (bead side) additionally recognises a directly-following parenthetical via `classifyParenthetical` — `R9(a)` becomes a sub-lettered claim with exact key `R9a`. `extractSpecTokens` (spec side) runs only `claimTokenRe`, so a spec that writes `R9(a)` indexes base `R9` but never exact `R9a`, and the claim fails as dangling. `AC9` (no hyphen) matches neither side and is silently never a claim. Dotted sub-numbers (`R6.3`, the house style since spec 128) degrade to base `R6` on both sides, so they resolve — at base granularity only.

**F. `--allow-not-ready` is all-or-nothing.** `next.GateReadiness(root, beadID, allowNotReady bool)` returns every failing signal when the boolean is set; `cmd/mindspec/next.go` registers the flag as `Bool`. `RecordReadinessOverride` writes `mindspec_readiness_override: {signals, overridden}`. `cmd/mindspec/bead_ready.go` evaluates and renders but never reads that marker, and nothing compares the recorded signals with the currently failing set — so a bead overridden for MF-3 reports FAIL forever, and an override recorded for a signal that later passes is never flagged as unnecessary.

**J. Governance.** `.mindspec/adr/` ends at `ADR-0044`; `0045` is free. `.mindspec/policy/` does not exist and no domain's `OWNERSHIP.yaml` claims it (claimed roots today: `internal/**` by domain, `cmd/**`, `plugins/mindspec/**`, `.claude/**`, `.gitignore`, the four OWNERSHIP files themselves), so a rule table there would need an ownership claim before any bead could land it under the ADR-divergence gate.

### Corrections to the diagnosis

- **A — "a named positional on an empty set is silently ignored"** holds on the CLAIM path only; on `--emit-only` a positional never consults the set at all (pinned 128 R6.1 preview semantics). `--pick N` on an empty claim-path set is ignored the same way; added to R1.3.
- **B — the brief's cap-site list is complete** and `doctor`'s `bd list --json` is correctly absent from it (schema probe, no row read). Recorded so the plan does not "fix" it.
- **C — the fact is already half-written.** `metadata.spec_id` is written by plan approve and is filterable via `--metadata-field`; bd's `--spec-id` field is NOT filterable and not surfaced by `bd show --json`. R3 therefore standardises on `metadata.spec_id` (one home) and does not add labels or `--spec-id` (two more homes for one fact).
- **D.4 — the message conflation is readiness-side,** not lifecycle-side: `ErrLandedMergeNoCandidate` already exists and wraps the broader sentinel; `evaluateMF3` just tests the broader sentinel first. The fix is the arm order, plus message text.
- **D.3 — ordering is `panel.Scan`'s path sort,** not an unspecified "scan order"; confirmed by reading `panel.Scan` (sort by `Dir`) and `panel.ForBead` (order-preserving).
- **ADR-0045 text —** "content-sha provenance" is not how `internal/setup` matches historical skills: `previouslyShippedSkills` (`internal/setup/skills.go`) matches byte-exact prior snapshots. Corrected in the ADR to "byte-exact snapshot provenance". The ADR's other Context claims were verified: `ms-bead-cycle`'s flow line "≥ N−1 APPROVE → merge terminal" vs `ms-panel-tally`'s "floor, not a sufficient condition" vs the binary's leg-(9.5) unresolved→Block (`internal/panel/gate.go`); `ms-bead-cycle` picks the lowest-numbered bead while `ms-spec-autopilot` picks the lowest-depth bead; `ms-bead-cycle` says a dissenting verdict may be "filed as a follow-up bead before merge" while the gate blocks on any unresolved REQUEST_CHANGES; the installed `.claude/skills/ms-bead-cycle/SKILL.md` (last commit 2026-07-07) is older than `plugins/mindspec/skills/ms-bead-cycle/SKILL.md` (2026-07-24).

## Requirements

Diagnostic strings are first-class outputs: ACs pin what a message says and what state it claims, red-on-revert, never that a string is non-empty. No AC executes an emitted recovery string; a hinted command's outcome is asserted by invoking that command's own code path on the fixture.

### R1 — Spec-scoped selection honesty (#255)

1. **One membership predicate.** Spec membership for selection is a single exported function (working name `next.SpecMembers(root, specID) (members, nearMisses, error)`) used by `BuildReadySet` on both paths. A bd-ready bead is a MEMBER iff it is a descendant of the spec's epic (`bd ready --parent <epic> -n 0`) OR it carries `metadata.spec_id == <spec-id>` (`bd ready --metadata-field spec_id=<spec-id> -n 0`); the two result sets are unioned by ID with bd's returned order preserved (first occurrence wins). The title-substring filter (`containsSpecID`) is REMOVED as a membership input once the predicate exists: a member is selectable whatever its title says; a non-member is never selectable whatever its title says. (OQ-2 records the alternative of keeping the title filter as a third disjunct and why it is not recommended.)
2. **Near-misses are named, never silent.** When the scoped member set is EMPTY, the predicate additionally scans the uncapped global ready set for beads whose title references the spec ID but which are not members, and the output names each by ID with the true reason — `bead <id> is bd-ready and its title names spec <spec-id>, but it is neither a descendant of epic <epic-id> nor linked by metadata.spec_id (parent: <parent-id or none>)` — followed by a recovery line `bd update <id> --parent <epic-id>` (parent SET is not the bk5t-buggy detach; raw `bd update --metadata` stays banned per ADR-0035). The scan runs only on the empty-set path (one extra bd call, never on the common path).
3. **A supplied selector on an empty set is refused, not ignored.** On the claim path, when the member set is empty and a positional bead ID or `--pick N` (N ≥ 1) was supplied, `next` exits non-zero with a refusal naming the selector and the emptiness (`no ready work for spec <spec-id>; positional <id> cannot be claimed from an empty ready set` / `--pick N is out of range: 0 items`) — never "No ready work found." exit 0. A positional that IS bd-ready but is not a member gets R1.2's membership sentence as its error, never "not found or not ready". `--emit-only`'s positional bypass (`FetchBeadByID`, pinned 128 R6.1) is unchanged and keeps its disclosure line.
4. **The empty-set result carries the spec's derived state, so emptiness is never completion evidence.** When the member set is empty and no selector was supplied, the output (exit 0, nothing mutated) prints, from an UNCAPPED child list of the epic: the lifecycle-children tally (`closed / in_progress / open`), the status-aware derived phase (`phase.DerivePhaseWithStatus`-class over that child set — the same derivation `state show` uses), and ONE phase-appropriate next line: `review` → `recovery: mindspec impl approve <spec-id>`; `implement` with an in-progress bead → the existing worktree-recovery branch (unchanged); `implement` with open beads and none ready → `all <n> open beads are blocked; recovery: bd blocked --parent <epic-id>` (or the `bd` invocation the plan verifies exists); `plan` → `recovery: mindspec plan approve <spec-id>`. The sentence "an empty ready set is not evidence the spec is complete; the derived phase above is" is printed verbatim. The same rule is stated once in `internal/instruct/templates/implement.md` (L3), so an orchestrator reading guidance sees it next to the verb that prints it. A failed child read renders the indeterminate form (128 R2.3's class), never a fabricated tally.
5. **Exclusion notices name IDs.** `ReadySet.ExclusionNotice` (retained for any residual non-member drop the plan keeps reporting, e.g. the R1.2 near-miss list) renders every excluded bead ID via `idrender.Bead`, not a bare count.

### R2 — No silently truncated bd row set

1. **Every row-consuming bd `ready`/`list` call passes `-n 0`.** The enumerated sites: `next.QueryReady`, `next.QueryReadyForEpic`, `next.ResolveActiveBead`, `lifecycle.listClosedBeadsFn` (orphans), `lifecycle.listOpenBeadsFn` (stale-open), `bead/hygiene.go`'s two `ListJSON("--status=open")` calls, `complete`'s post-close `runBDFn("ready", "--parent", …)`, and every call R1/R3 add. The one rationale-carrying exclusion is `internal/doctor/beads.go`'s schema-drift probe (`bd list --json`), which reads no rows; it carries an in-code allowlist marker the R2.3 lint recognises.
2. **Through one waist.** All of them route through `internal/bead` helpers (`ListJSON` and a new `ReadyJSON`) that append `-n 0` by construction unless the caller passes an explicit `-n`/`--limit`. Argument-recording seam tests pin the argv.
3. **Anti-drift is mechanised.** A lint test in `internal/lint` (working name `TestBDRowCapWaist`) walks non-test Go sources and fails on any bd argv literal beginning `"ready"` or `"list"` outside `internal/bead` that lacks the allowlist marker (`// rowcap-allowlisted: <reason>`), and on any waist invocation that would reach bd without `-n`. **Defence in depth:** the waist captures stderr separately on SUCCESS and, when bd prints a truncation notice (the `Showing N of M` form) on a zero exit, returns an error `bd truncated the row set (<escaped notice>) — mindspec never requests a cap; upgrade bd or report` with an ADR-0035 recovery line — so a future bd default change can never silently re-truncate.
4. **Version note, not a floor change.** `doctor`'s `bdVersionFloor` stays `1.0.4` (the `-n 0` form is already relied upon by `phase.Cache` at that floor). If planning finds a floor version where `-n 0` is NOT unlimited, R2.3's success-path notice detection is the guard and the floor is raised in that bead with the evidence.

### R3 — One queryable spec-linkage datum, written at creation

1. **The datum is `metadata.spec_id`** (the key `approve/plan.go` already writes on every lifecycle bead). `approve/spec.go`'s epic `bd create` ALSO writes `spec_id` into its initial metadata (today: `spec_num`, `spec_title`, `mindspec_phase`). No labels and no `bd --spec-id` are added: labels would be a second home for the same fact, and bd's `--spec-id` field is neither filterable nor exposed by `bd show --json` (verified).
2. **Pinned, not hoped.** A test over the `bd create` argv (`planRunBDFn` / `specRunBDFn` seams) asserts both call sites carry `spec_id` and that the value passes `idvalidate.SpecID`. R1.1's `--metadata-field spec_id=<id>` query reads exactly this key.
3. **No migration.** Existing epics (which lack `spec_id`) and historical beads remain members via the descendant disjunct of R1.1; the predicate is a union precisely so that no backfill is required. A `doctor` nudge for linkage-less lifecycle epics is a Non-Goal.

### R4 — MF-3 tells the truth (#239, #232)

1. **Dependency scoping.** `evaluateMF3` holds a closed `blocks` dependency to the landed-merge test ONLY when the dependency is a lifecycle bead of the SAME spec (a member per R1.1's predicate, resolved through the existing `findEpicForBeadFn` lineage — never by title). A closed non-member dependency PASSES on bd-closed alone and the rendered report says `dependency <id>: closed; not a bead of spec <spec-id> — landed-merge test not applicable`. A non-closed dependency of either kind still fails as today.
2. **Ancestry-based candidate discovery.** `lifecycle.FindLandedMerge`'s candidate generation considers every two-parent merge commit REACHABLE from the spec-branch tip (a new `gitutil` primitive beside `FirstParentMerges`, e.g. `git log --merges --format=… <ref>` without `--first-parent`) whose subject names `bead/<id>` by full branch-name equality (the AC-2f no-prefix-collision rule, unchanged). Everything downstream — same-second-parent grouping, the three corroboration legs, the oldest-anchored revert/reapply discrimination — runs unchanged over that candidate set. `ExactSecondParentMerges` (the merge-time binding writer and `reattest`'s nominator) must identify the same candidate set `FindLandedMerge` does, or `reattest` cannot write the binding `ready-check` asks for: the plan either routes both through the one new primitive or records why first-parent is correct at the binding WRITE site only (OQ-4).
3. **Panel-leg semantics (amends ADR-0041 § Spec 125 item (c), priced above).** `reviewedHeadSHAForBead` becomes a SET lookup: all non-empty `reviewed_head_sha` values across every registration `panel.ForBead` returns. The leg CONFIRMS iff the set contains the candidate's exact second parent; a non-empty set that does not contain it is NON-CORROBORATING — it neither confirms nor pre-empts the surviving-tip and landed-binding legs, which keep their exact-equality contradiction semantics unchanged. All three legs are evaluated before any contradiction is returned, and a returned contradiction names the datum that contradicted. The set alone never confirms an ancestor (settled fact 4).
4. **Messages say what is true.** `evaluateMF3` discriminates, in this order: `*LandedMergeNoEvidence` (unchanged: candidate exists, no admissible datum → `mindspec reattest`), `errors.Is(err, lifecycle.ErrLandedMergeNoCandidate)` (the ONLY arm allowed to print "no landed merge into <spec-branch> names bead/<id>"), then the remaining `ErrLandedMergeNotFound` wrappers rendered as what they are — `a merge naming bead/<id> exists (<sha>) but <datum> contradicts its second parent <sha>` or `merge <sha> naming bead/<id> was reverted or cleanly removed after landing` — each with its own recovery line (inspection first; never `mindspec complete` for a bead whose merge exists).
5. **#232 disposition.** No remote-tracking ref is read on this path (evidence in Background). A fixture with the spec branch locally ahead of its remote-tracking ref (the "one push at end of spec" state) PASSES MF-3; the issue is closed by R4.1–R4.4 with that fixture as the regression guard. No `origin/`-aware mode is built.

### R5 — MF-2 form symmetry

1. **One form table, both sides.** The claim forms the bead-side harvester recognises and the spec-side indexer recognises are the SAME set, pinned by one shared table: appended sub-letter (`R9a`, `AC-2b`), parenthetical sub-letter (`R9(a)`, `AC-2(b)`), Roman-enumerator parenthetical degrading to base (`R5(ii)`), bare base (`R9`, `AC-9`), and — decision — hyphenless `AC<n>` NORMALISED to `AC-<n>` on both sides (so `AC9` in a bead resolves against `AC-9` in the spec and vice versa; it never dangles on form alone). Dotted sub-numbers (`R6.3`) continue to resolve at base granularity on both sides, and the table says so (OQ-6 records the indexing alternative).
2. **Symmetry is tested, not asserted.** A table-driven test (`TestMF2_FormSymmetry`) runs every form through `extractLineClaims`-class harvesting and `extractSpecTokens`-class indexing and asserts each harvested key is producible by the indexer from the same text; the existing `TestReadiness_MF2AllClasses` gains the `R9(a)`-in-spec and `AC9` legs.

### R6 — Signal-scoped `--allow-not-ready` with evidence; `ready-check` reads it back

1. **Scoped form.** `--allow-not-ready=<MF-ids>` takes a comma-separated list of signal IDs (`MF-1`…`MF-4`). `GateReadiness` proceeds iff the currently failing set is a SUBSET of the named set; if any OTHER signal fails, it refuses with the standard NOT-READY report plus `recovery: <this exact invocation with --allow-not-ready=<all currently failing ids>>`. Naming a signal that is not failing is accepted and reported as `MF-x named but passing — not recorded`. The BARE flag (no value) REFUSES with that same filled-in recovery line (OQ-5 records the compatibility alternative and why refusal is recommended).
2. **Evidence in the marker.** The scoped override REQUIRES `--evidence <path>`: a readable file whose contents justify the bypass. `RecordReadinessOverride` stores, under `mindspec_readiness_override`, the signals actually overridden (the failing ∩ named set), the RFC-3339 timestamp (today's field), and `evidence: {path, sha256, bytes, text}` where `text` is the file content (UTF-8, control bytes escaped at render) up to 4 KiB; a larger file refuses before any mutation. The marker-before-claim, fail-closed, rollback-on-claim-failure contract (settled fact 2) is unchanged.
3. **`ready-check` honours the marker.** `mindspec bead ready-check <id>` reads `mindspec_readiness_override`; a signal that fails AND is recorded renders `MF-x: OVERRIDDEN (recorded <timestamp>; evidence <sha256-prefix> <path>)`; the command exits 0 iff every failing signal is recorded (`report.AllPassOrOverridden()`), and non-zero naming the UNCOVERED failing signal(s) otherwise. A recorded signal that now PASSES renders `MF-x: PASS (override recorded but no longer needed)` — informational, exit unaffected. `GateReadiness` on a re-claim (after `mindspec release`) applies the same subset rule to an existing marker, so an already-overridden bead does not demand a second override for the same signals.
4. **Guidance follows.** `cmd/mindspec/bead_clarify.go`'s text and `project-docs/user/guides/autonomy.md` name the scoped form; the bare-form sentence is removed everywhere the doc-sync gate reaches.
